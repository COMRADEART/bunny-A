================================================================
0. T9 PURPOSE
================================================================

T9 must solve one specific UX problem:

Desktop/computer automation currently asks the user for too many repeated
approvals during a single bounded workflow.

T9 must reduce approval fatigue WITHOUT turning:

"Approve this action"

into:

"Control my whole computer."

The property to establish is:

A user may deliberately authorize a narrow batch of predictable low-risk
desktop actions, while anything outside that exact envelope still requires a
new approval.

No renderer-local:

================================================================
7. ELIGIBLE ACTIONS
================================================================

Only low-risk, predictable desktop actions should be batch-eligible.

Examples may include:

focus known application
click known UI control
select tab/menu
scroll
type non-sensitive ordinary text
move through deterministic UI
read visible UI state
safe local navigation

Eligibility must come from Bunny's risk model, not from the model saying:

"This is safe."

Do not create an exhaustive brittle string list if Bunny already has structured
risk classes.

Use structured policy.

12. ACTION COUNT LIMIT
================================================================

A batch grant must have a finite action budget.

Example concept:

max 10 desktop mutations

Do not choose this example value blindly.

request new approval.

13. TIME LIMIT
================================================================

Use a short bounded duration appropriate to desktop interaction.

Expiration uses Host time/state, not client UI timers as authority.
