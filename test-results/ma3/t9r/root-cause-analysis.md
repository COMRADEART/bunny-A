# Calculator acquisition and focus root cause

Microsoft Calculator 11.2607.0.0 on Windows 11 build 26300 is installed in interactive session 1. Its top-level `ApplicationFrameWindow` belongs to System32 `ApplicationFrameHost.exe`; arithmetic controls belong to the signed Calculator package's distinct `CalculatorApp.exe` process.

Controlled minimization keeps the same HWND and frame process lifetime but detaches the XAML content surface: `num0Button`, `num2Button`, `clearButton` and `CalculatorResults` are absent from the live UIA tree. The original acquisition reused an existing root only after demanding its arithmetic controls; restoration occurred later during focus, so acquisition could fail before reaching restoration. `IsOffscreen` did not describe this state reliably; the native `IsIconic` predicate did.

Cold original X53 succeeds, minimized original X53 reproduces the exact failure, and repaired minimized X53 restores the same frame/content lifetime and succeeds. The T8-to-T9 native acquisition, X53 and worker source paths are byte-identical. This is evidence of a pre-existing native readiness defect, not a demonstrated T9 security-source regression. The historical T9 failure did not log its minimized flag, so the exact earlier workstation state cannot be reconstructed.

The repair distinguishes native frame identity from control readiness. Before restoration it validates current HWND/native owner PID, frame lifetime/session/executable/class, and the native AppUserModelID against the signed installed Appx manifest. A cached bound target additionally requires its exact content process lifetime and signed executable. Only an admitted open operation may restore. Pure preparation probes do not restore, launch or invoke. Every ready result requires a fresh full UIA tree, expected semantic enabled controls and the original package/content/dialog checks. Waiting is condition-based at 100ms intervals, at most 8 seconds per readiness phase and always bounded by consent expiry and the operation timeout. Launch discovery has a separate bounded 8-second phase; no indefinite retry or uncertain automatic relaunch occurs.

A later preserved stability failure had valid arithmetic identity but Windows denied one-shot `SetForegroundWindow`, leaving another app foreground. The repair adds semantic UIA focus on the freshly verified target, with a two-second condition deadline and current consent/lifetime revalidation. It does not attach foreign input queues, change system foreground-lock policy, synthesize keys or invoke a button to obtain focus. Native HWND foreground equality remains mandatory before arithmetic invocation; unavailable focus still fails.

Microsoft references: [IsIconic](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-isiconic), [IsOffscreen](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.automationelementinformation.isoffscreen?view=windowsdesktop-10.0), [native window property store](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shgetpropertystoreforwindow), [AppUserModelID](https://learn.microsoft.com/en-us/windows/win32/properties/props-system-appusermodel-id), [semantic UIA focus](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.setfocus?view=windowsdesktop-10.0), [foreground restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

Restoration evidence initially was overwritten by a subsequent successful validation reporting `restored:false`. That audit defect was repaired and a new regression test ensures the first acquisition receipt is preserved. Both failed evidence harness attempts remain available.

## Addendum: preserved stability failures and the final matrix

- **Attempt 4, run 8 (ea48c40).** Seven consecutive passes, then run 8 timed out with `Timeout: Integrated Mission completion`. Its receipts (`stability-attempt-4/08-warm/integrated-attempt.json`) show acquisition, focus, Clear and the first read succeeding on the same verified frame/content lifetime. The second `computer.invoke_control` (`num2Button`) was then refused with `Foreground drift requires a fresh decision.`: another window had taken the foreground between steps. This is the designed fail-closed outcome. No arithmetic is invoked without native foreground equality, and drift is never auto-corrected. The Mission correctly waited for the user, and the unchanged test timed out waiting for completion. The cause is environmental, not a readiness or identity defect, and was not "fixed" by weakening the foreground check. The run was retained and not silently retried; a new full matrix was started instead.
- **Attempts 5–6 (395d1c0).** The ownership guard in `owned-target-control.ps1` refused twice, before any X53 run. First, the previously ledgered HWND no longer existed. Second, the re-ledgered entry lacked the required test-owned provenance fields. The ledger was then rebuilt from the canonical Host launch receipt of the current window, with exact frame/content lifetime equality (`owned-calculator-ledger.json`).
- **Final source 395d1c0.** `x53-stability-matrix.json` has 10/10 consecutive clean runs (3 cold launches, 5 warm reuses, 2 minimized with admitted restoration), plus the X53 run inside the complete regression: 11 consecutive clean live executions in total. X53 also passed in the full regressions of ea48c40, b345aa3 and 0904132 during this session.
