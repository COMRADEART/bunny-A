**Short answer:** every provider session in the codebase starts at one of two calls inside the private `M.launch()`. A consent check at those two points covers first launches, retries, reroutes, effort escalations and restart paths. A search found no other `adapter.launch` call site in src/lib.

## 1. Where the final provider is chosen and launched

There is one router in three layers:
- **Provider filter:** `bunnyRoute()` and `eligibility()` in router.ts (lines 55 and 24). `eligibility()` enforces `providerAllowlist`/`providerDenylist`, local-only rules and readiness.
- **Model router:** `buildCandidates` → `hardExclusions` → `scoreCandidate` → `selectRoutingCandidate` in routing.server.ts.
- **Manager glue:** `routingPipeline()` (M:706), `revalidateCandidate()` (M:820), `rerouteFromDecision()` (M:845).

**Approval entry points.** All of these call `M.launch()` (M:1408):
- `approve()` (M:1355), used by HTTP "approve" and by Mission "provider.execute" answers (MM:4440).
- `approveVoiceTurn()` (M:1328).
- `approveDelegated()` (M:1377), called by `launchModel` (MM:1633) and `launchTeamModel` (MM:1724). Its `check` is `taskViolation()` (authorization.server.ts:494), which checks `envelope.providers.allow`.

**What `launch()` does, in order:**
1. Basic refusals: state must be waiting_for_approval, restart-survivor check, project/cwd, Mission scope check, `eligibility()` and the local-only rule (:1415–1447).
2. An automatic reroute after approval (:1451–1504), covered in section 2.
3. A fresh `db.get(id)`, then the final Mission checks (:1510–1521): `missionScopeCheck(final,"check")`, `missionAttemptAdmission(final,"action")`, then `missionScopeCheck(final,"launch")`, which uses up a single-use trusted-desktop grant.
4. The state moves to "launching" (:1522).
5. **Choke point A**, the first dispatch: `adapter.launch(adapterTask, adapterHooks)` at M:1745, with a frozen copy of the Task.

**Choke point B, every relaunch:** the `startSession()` closure (M:1647–1736) ends in `targetAdapter.launch` at M:1723. Before that it re-checks `eligibility`, local-only and the Mission hooks, and writes the new provider/model/effort to the Task. Direct (non-Mission) Tasks get no other per-relaunch authority check.

**Recovery loop** (M:1784–2020): `classifyFailure` → `saveAttempt` (:1881) → `planRecovery` (:1915), then one of:
- retry on the same candidate (:1929);
- raise effort (:1943), falling back to `rerouteFromDecision` when no higher effort exists;
- reroute or reroute-to-larger-context (:1967).

Manual selections never reroute (:1925). The limits are 1 same-candidate retry, 2 alternates and 4 attempts in total.

**Adapters** (adapters.server.ts):
- `OllamaAdapter.launch` (:172) makes an HTTP call through `execute()` in orch/exec.server.ts.
- `CodexAdapter.launch` (:471) and `ClaudeAdapter.launch` (:538) go through `spawnSession` (:212).
- opencode, cline and cursor use `DetectOnlyAdapter` (:581). They are always "unavailable", `launch()` throws, and routing excludes them.

**After a Host restart:**
- The constructor (M:191–211) marks every launching/running/verifying/waiting Task as failed. Running Tasks are never relaunched automatically.
- Tasks in `waiting_for_approval` survive with their old provider and decision record. Approving one later goes through `launch()`, where it may be rerouted.
- Mission steps interrupted by the restart are put back to "ready" by `reconcileInterrupted()` (MM:4767). They are then resubmitted through `launchModel` as a new Task under the same stored envelope.

**Agents:** the Agent runtime does not route or launch anything itself (agent-runtime.server.ts:22). Everything goes MissionManager → `tasks.submit(delegated)` → `approveDelegated` → `launch()`. MissionManager installs its hooks on the Task manager at MM:155, :184, :328, :329 and :340. The Mission scope check does not re-check `envelope.providers.allow` itself. Reroutes stay inside the allowed list only because `task.constraints.providerAllowlist` (the envelope's list intersected with the step's, MM:1450–1487) is re-checked by `eligibility()`.

## 3. Consent and approval data recorded today

- **`OrchTask.approval`** (types.ts:248) is saved only for Mission approvals (M:1527). Direct user, device and voice approvals exist only as events: `approval.accepted`, `approval.remote_device`, `approval.voice_tool_free`, `approval.delegated`. The device-approval set is in memory only.
- **Other relevant Task fields:**
  - routing: `manual`, `routingMode`, `routingDecisionId`, `routingRerouted`, `decision.decision_assistance`;
  - authority (cannot be changed through `update()`, M:396): `executionScope`, `mission`;
  - scope: `projectId`, `cwd`, and `constraints` (allow/deny lists, `localOnly`, `offlineOnly`, `cloudOnly`, `privacyLocal`, model pins).
- **`Project.preferred`** is always "auto" and routing never reads it.
- **Mission envelope** (`AuthorizationEnvelope`, missions/types.ts:99): `providers {execution, allow, localOnly, sessions{steps, maxSessions, writeIncludesShell}}`, `grantedBy`, `expiresAt`, `revokedAt`, `budget.maxExternalModelCalls`. It is stored in `mission_authorizations`.
- There is no per-provider, per-account or per-project consent anywhere, and no account identity beyond `authenticated`/`authenticatedState`.
- **Ambient API key:** `spawnSession` passes `{...process.env}` minus CLAUDECODE to Codex and Claude (adapters.server.ts:227 and :351). An ambient `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY`) therefore reaches the CLI and can switch subscription work to paid API billing. Nothing removes it today.

## 4. How the routing record is persisted

- **Tasks:** `tasks(id, record JSON)` (persistence.server.ts:22). New Task fields need no migration.
- **Audit and learning:** `events(sequence, at, type, task_id, detail)` and `outcomes(task_id, provider, task_type, completed, verified, duration_ms)`.
- **Routing store** (routing-store.server.ts:142; tables created in its constructor, no `user_version` change):
  - `routing_decisions(id, task_id, mission_id, created_at, policy_version, decision JSON)`, written with INSERT OR REPLACE, so retarget and reroute counts overwrite the same row.
  - `routing_attempts(id, decision_id, task_id, attempt_index, provider, model, effort, taxonomy, detail, created_at)`.
  - `model_routing_profiles(provider, model, provenance, profile, updated_at)`.
  - Rows whose policy version is not "routing-policy-v1" read back as null. Bumping the version would break reroutes for Tasks already in flight.
- **`jev_usage`** (typesafe-jev.server.ts:236) has an index on `at` and is never pruned.
  - `usage()` (:325) needs today's rows, every row for the current session, and the latest billable row.
  - A safe retention rule: delete rows older than N days, excluding the current session and any 'pending' row. Run it when `JevService` is constructed and once a day.

## Recommendation: where to put the dispatch-time consent check

1. **Primary gate.** Add `dispatchConsent(task, "launch"|"retry"|"reroute")` on `TaskManager`, backed by a Connection Registry passed in through `ManagerOptions`. It should fail closed and cover all six providers, including Ollama cloud tags. Call it in exactly two places:
   - **In `launch()`, right after `final = this.db.get(id)` (M:1510).** It must come before the Mission admission and grant-spending checks, so a refusal never uses up a desktop grant. Throw there; the Task stays waiting_for_approval because the "launching" update at :1522 hasn't happened yet.
   - **In `startSession()`, right after `targetTask` is built (M:1667).** On refusal, emit `routing.consent_denied` and return null; the loop then fails the Task with a truthful note.

   These two calls cover P3–P6, P8 and P10.
2. **Consent-aware reroutes.** In `rerouteFromDecision`, skip candidates the gate would refuse (like the device skip at :885), so refused targets don't use up the 2-alternate limit.
3. **Close limitation 7 at routing time as well.** Add a consent exclusion callback to `buildCandidates`, modelled on `layaGate` (routing.server.ts:121, :445; wired at M:729). Candidates without consent then never reach Jev or the fallback order, and the decision record shows the exclusion reason. Alternatively, extend `CandidateTraits` with vendor/connection and refuse cross-vendor advice in `applyDecisionAdvice`. Keep the primary gate either way, because consent can be revoked after submit and waiting Tasks survive restarts.
4. **Record consent on the Task.** At M:1522, save `approval` for all approval kinds, plus a snapshot of the consent that was approved: `{connectionId, mode, provider, projectId, revision}` in the task JSON. Keep a `connection_consents` table owned by the registry, created the same additive way as the routing tables. A reroute outside the approved consent should be refused or sent back for approval.
5. **Ambient API keys.** Remove `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` at adapters.server.ts:227 and :351 unless that provider's connection mode is "api_key" with explicit consent. Drive this from a connection-mode field on the frozen Task copy, never a credential handle.

**Decision needed:** what existing owners get on first boot, since the gate fails closed. Options are a one-time Connected Accounts review, or automatically carrying over consent for providers that already have outcome rows.
