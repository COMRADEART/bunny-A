## (a) What Sign in with ChatGPT (SIWC) gives a third-party app
There are two separate grants.

**1. Identity only** (scopes `openid profile email`)
- quickstart: "Identity scopes don't grant access to ChatGPT conversations or OpenAI API resources."
- It is gated. quickstart: "currently available to selected commercial partners through a limited trial."
- request-client-id: "To join the waitlist, complete the Sign in with ChatGPT interest form."
- Result: it needs a client ID issued by OpenAI. Bunny cannot build this without registering.

**2. ChatGPT plan usage ("token sharing")**
- quickstart: "ChatGPT plan usage is available to all open-source partners and selected private clients." It "doesn't grant access to the user's API key or conversations."
- token-sharing-open-source: "These docs explain ChatGPT plan usage for open-source and locally hosted apps." / "If you're interested in offering it in a paid or remotely hosted app, complete the interest form."
- Registration happens during sign-in. The first authorize call sends `client_id=dynamic_agent_client` and the callback returns an issued client_id. sign-in page: "This direct flow needs neither a client secret nor a partner API key."
- Endpoints:
  - authorize: `auth.openai.com/api/accounts/authorize`
  - token: `.../oauth/token`
  - resource: `https://api.openai.com/v1`
- Plan scopes: `offline_access resource.invoke chatgpt.tokens.use.direct`. "A valid ID token alone does not authorize ChatGPT plan usage."
- Flow: PKCE S256, state and nonce, callback on `127.0.0.1` loopback (not `localhost`), an opaque per-host `ext_agent_host_id`, and `agent_name_hint`.
- Token rules:
  - Files written atomically with 0600 permissions.
  - "Keep tokens out of browser storage, source control, logs, analytics, and support transcripts."
  - Serialize refreshes (the refresh token rotates).
  - Revoke on sign-out.
  - "Never combine one registration's client ID with another registration's tokens."
- Preview limitations:
  - Requests must set `store:false` and `stream:true`.
  - Not supported: image generation, file search, Code Interpreter, computer use, hosted MCP, `tool_search`, audio input.
- Sharing: users can set per-app limits, and the Plus five-hour limit is shared across apps. This comes from the fetch tool's paraphrase, not an exact quote.

**Eligibility problem for Bunny:** package.json:3 has `"private": true` and the repo has no LICENSE file. Whether a private, unlicensed, locally hosted app qualifies for the dynamic open-source path is ambiguous and unverified. Treat SIWC token sharing as deferred until Bunny is published under an OSS license or OpenAI confirms eligibility.

## (b) Can Bunny drive the user's installed Codex CLI under their plan?
This is documented as an integration surface:
- app-server is "the interface Codex uses to power rich clients"; "Use it when you want a deep integration inside your own product."
- "`codex exec` reuses saved CLI authentication by default."
- The user signs in themselves (`codex login`, `--device-auth`, or app-server `account/login/start` with chatgpt / chatgptDeviceCode).

I found no text that forbids this, and none that explicitly blesses it; the terms are unverified.

Constraints:
- "The app-server command and WebSocket transport are experimental and aren't supported for production workloads." stdio is the default transport. Non-loopback WebSocket allows unauthenticated connections by default.
- "Clients must send a single `initialize` request per transport connection." "Use `clientInfo.name` to identify your client for the OpenAI Compliance Logs Platform." Keep Bunny's `bunny_a_host` name stable.
- "Treat `~/.codex/auth.json` like a password: it contains access tokens."
- ChatGPT-managed auth in CI: "Do not use this workflow for public or open-source repositories."
- With ChatGPT sign-in, usage follows ChatGPT workspace permissions and retention.

Alternative SIWC path (codex-app-server page): Bunny owns the OAuth token and runs `codex app-server --listen stdio://` with a custom provider. The settings are `env_key="ACCESS_TOKEN"`, `requires_openai_auth=false`, `wire_api="responses"` and `supports_websockets=false`.
- "Your app must refresh the OAuth token." After a refresh, restart app-server and call `thread/resume`.
- model/list is "a catalog, not an entitlement check". Only a turn status of `completed` means success.
- This path is blocked by the eligibility question in (a).

## (c) Detecting auth mode without reading auth.json
**`codex login status`** (source: cli/src/login.rs `run_login_status`)
- Prints to stderr.
- Exit 0 with one of: "Logged in using ChatGPT", "Logged in using an API key - <masked>", "...access token", "...personal access token", "...Amazon Bedrock ...", "Logged in using workload identity".
- Exit 1 with "Not logged in" or "Error checking login status: …".
- Problem: it calls `load_auth(enable_codex_api_key_env=false)`, so it ignores `CODEX_API_KEY`.

**app-server `account/read`** (preferred)
- Request params: `{"refreshToken":false}`.
- Returns `account` as null when signed out, otherwise `{type:"apiKey"|"chatgpt"|"amazonBedrock", email, planType}`, plus `requiresOpenaiAuth`. Bunny must redact `email`.
- Notifications: `account/updated` (with `authMode` and `planType`) and `account/rateLimits/updated`.

**`account/rateLimits/read`** returns `rateLimitsByLimitId.codex` with `{primary,secondary}:{usedPercent,windowDurationMins,resetsAt}`, plus `rateLimitResetCredits` and `credits` when present.

**Credential precedence, verified in source** (manager.rs `load_auth`):
1. `CODEX_API_KEY` env, when the entry point enables it. The source comment says "API key via env var takes precedence over any other auth method."
2. Ephemeral external ChatGPT tokens.
3. `CODEX_ACCESS_TOKEN` env.
4. The stored credentials (file, keyring or auto).

Which entry points read `CODEX_API_KEY`:
- On: `codex exec` (exec/src/lib.rs:745), and per the docs also `codex review`, the TypeScript SDK and `exec-server --remote`.
- Off: app-server (app-server/src/lib.rs:551,585), the TUI (tui/src/lib.rs:726) and `login status`.

`OPENAI_API_KEY` is not an auth source for exec or app-server. It is used in two places:
- TUI login prefill (tui/src/onboarding/auth.rs:852).
- Realtime conversation falls back to it silently even in ChatGPT/SIWC sessions (core/src/realtime_conversation.rs:1939-1944, marked "temporary fallback").

**Hazard: `forced_login_method`.** The docs say: "If the active credentials don't match the configured restrictions, Codex logs the user out and exits." In source, the check loads with the env key enabled. So `forced_login_method="chatgpt"` plus an ambient `CODEX_API_KEY` calls `logout_with_message`, which deletes the user's stored login. Bunny must never use it as a guard.

## (d) Billing separation
- auth docs: "Sign in with ChatGPT for subscription access" versus "Sign in with an API key for usage-based access."
- "When you sign in with an API key, Codex uses standard API pricing instead of included ChatGPT plan credits."
- "OpenAI bills API key usage through your OpenAI Platform account at standard API rates." API-key usage follows the API organization's retention settings.
- pricing: "API token prices are separate from subscription usage." Plans that include Codex: "ChatGPT Free, Go, Plus, Pro, Business, Edu, or Enterprise." "Pro plans currently have no five-hour limit"; "Weekly limits may also apply." Credits are "the unit used to pay for eligible usage on credit-based plans."
- SIWC errors page: "OpenAI does not silently switch the request to another billing path."
  - `subscription_sharing_usage_limit_exceeded` (429): "Pause new requests…"
  - `subscription_sharing_user_not_eligible` (403): "do not repeat the same request or loop through OAuth."
  - Using the user's own API key is offered only as an explicit choice the user makes. This supports the T13.2 rule against silent paid fallback.

## Current Bunny code T13.2 must change
- **Child env inherits ambient keys.** src/lib/bunny-host/adapters.server.ts:227 and :351 build the env as `{ ...process.env }` and only delete `CLAUDECODE`. The Codex dispatch at :569 is `["exec","--json",…,"--model",task.model,"-"]`. Since `codex exec` gives `CODEX_API_KEY` top precedence, an ambient key silently moves subscription work to paid API. This is the OpenAI equivalent of the `ANTHROPIC_API_KEY` problem.
- **Sign-in check cannot tell ChatGPT from API key.** In `CodexAdapter.detect`, adapters.server.ts:437-447 looks only at the `codex login status` exit code. That check also ignores `CODEX_API_KEY`, so the label can be wrong. The test fixture m2.test.ts:70 already models the "Logged in using ChatGPT" stderr line.
- **Probe env and missing `account/read`.** In src/lib/bunny-host/codex-probe.server.ts, :43 (Windows) and :63 (POSIX) pass the full env to the probe. That is harmless for app-server today, but should be scrubbed for consistency. Line :73 sends `initialize` with clientInfo `bunny_a_host`. Lines :75-84 read `model/list` and `account/rateLimits/read` but never call `account/read`. That is the documented way to get auth type and `planType`.

## Recommended rules for the Codex adapter
- **Connection mode:** derive it from `account/read.account.type` plus whether a consented key was injected, never from the ambient env.
- **Final-dispatch gate:**
  - Build the env from an allow-list, stripping `CODEX_API_KEY`, `OPENAI_API_KEY`, `CODEX_ACCESS_TOKEN` and `OPENAI_BASE_URL`.
  - Re-check `account/read`. If the type is not `chatgpt` on a subscription-consented task, refuse with no fallback.
  - Apply the same gate on retries and on any provider move advised by Jev; this closes T13.1 limitation 7.
- **Never pass `-c forced_login_method`.**
- **Keep `OPENAI_API_KEY` out of the env** unless API consent exists, because of the realtime fallback.

## Other providers (user: "even for all provider like ollama, opencode, etc")
**opencode** (opencode.ai/docs/providers/)
- Credentials are "stored in `~/.local/share/opencode/auth.json`"; `opencode auth list` shows what was added.
- It offers a "ChatGPT Plus/Pro" browser login.
- For Claude Pro/Max plugins the page says "Anthropic explicitly prohibits this", and they are no longer bundled since 1.3.0.
- Ollama connects to it as an OpenAI-compatible provider with `"baseURL": "http://localhost:11434/v1"`.
- Implication: show opencode auth state from `auth list` names and types only. Never route Claude subscription work through opencode.

**Ollama** (docs.ollama.com/cloud)
- Cloud API access uses `OLLAMA_API_KEY`; the app and CLI must "sign in to use cloud models" (e.g. `gemma4:cloud`).
- Users can "disable cloud features" to "use only local models".
- Implication: separate `local_runtime` (no account) from `cloud` (account and consent required). Treat an ambient `OLLAMA_API_KEY` like any other ambient key.
- Ollama cloud plan limits are unverified.
