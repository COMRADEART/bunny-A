## 1. Why Gate R1-G4 is `PARTIAL`

1. **Four live Windows Narrator rounds were executed with the workstation owner** on the installed candidate (`http://127.0.0.1:8084/?view=tasks`), covering:
   - **Round 1:** Main dashboard (`Tasks` navigation, `Execution history`, background-execution policy checkboxes, notification `Dismiss` / `Snooze 1 h` buttons, `New goal` disclosure button, goal `Pause` button, schedule/monitor `Turn off` button).
   - **Round 2 & 2b:** Goal creation empty-submit error announcement (`role="alert"` + focused `aria-invalid="true"` input with `aria-describedby` message) and Host preview focus move (`Review: New goal` heading, `Approve and start`, `Back to edit`).
   - **Round 3:** Approval Center & active task rows (action-level `file.apply` approval on `"Update Atlas notes"`: `Approve this action`, `Deny`, `Inspect details`, `Action details` region; task-level approval on `"Atlas status digest"`: `Approve`, `Cancel`).
   - **Round 4:** Dynamic live-region announcements while focus remained parked on `Execution history` during asynchronous task completion (`"Atlas status digest"` at `15:24:55 UTC`) and monitor change notification (`"Atlas build: now \"FAIL\"."` at `15:26:17 UTC`).
2. **Two genuine screen-reader defects were uncovered during live Narrator testing:**
   - **Finding N-1 (Missing item context on per-row action buttons — Rounds 1 & 3):** Per-item buttons (`Dismiss`, `Snooze 1 h`, `Pause`, `Turn off`, `Approve`, `Cancel`, `Approve this action`, `Deny`, `Inspect details` — `17` instances in `accessibility-audit.json`) expose only their bare action label without `aria-label` or `aria-describedby` context identifying which notification, goal, schedule, monitor, or task they act upon. When tabbing through multiple rows, a Narrator user hears `"Dismiss, button"`, `"Pause, button"`, or `"Approve, button"` without the target item's title.
   - **Finding N-2 (Unannounced asynchronous task/monitor status updates — Round 4):** Although `<Notice />` and `.proactive-status` render `role="status"` (`aria-live="polite"`, `aria-atomic="true"`), Windows Narrator did not speak either the task completion update (`15:24:55 UTC`) or the monitor `source_changed` notification (`15:26:17 UTC`) when focus was parked on `Execution history` (`Heard neither`).
3. **Owner ended manual listening after Round 4:** After Round 4, the owner reported that Narrator was not reading dynamic updates properly and stopped manual listening. The remaining screen checks (`Schedule creation`, `Monitor creation`, `Windows notch`) were completed via Chromium's computed Blink accessibility tree (`Accessibility.getFullAXTree`) and WPF XAML `AutomationProperties` inspection, which are explicitly distinguished below from live Narrator listening.

## 4. Visual, Motion, High Contrast, and Scaling Checks

Verified on the installed candidate (`Bunny-A-Windows-S2T3R1-6-TEST`) in [`docs/ma4-s2-t3r1/evidence/installed/accessibility-audit.json`](evidence/installed/accessibility-audit.json) and [`docs/ma4-s2-t3r/evidence/ui/ui-evidence.json`](../ma4-s2-t3r/evidence/ui/ui-evidence.json):

1. **Checkbox Sizing Regression Fix (`fade2b6`):**
   - In T3R, `.proactive-form input:not([type="checkbox"])` excluded checkboxes, but `.proactive input { min-height: 2.3rem }` still matched `<input type="checkbox">` inside `.proactive-policy`, stretching checkboxes vertically (`16x37 px`).
   - Fixed in commit `fade2b6` (`.proactive input:not([type="checkbox"])`, plus `width: 1.1rem; height: 1.1rem; min-height: 0; padding: 0` on `.proactive-policy input[type="checkbox"]`). Verified on the installed candidate (`18x18 px` square checkbox).
2. **Reduced Motion (`prefers-reduced-motion: reduce`):**
   - Emulating `prefers-reduced-motion: reduce` on `http://127.0.0.1:8084/?view=tasks` resulted in `animCount: 0` active CSS animations inside `[data-testid="proactive"]` (`accessibility-audit.json` check #10: `PASS`).
3. **High Contrast (`forced-colors: active`):**
   - Emulating `forced-colors: active` rendered all proactive cards, forms, and buttons cleanly with system colors and borders (`accessibility-audit.json` check #10: `PASS`; screenshot in `docs/ma4-s2-t3r/evidence/ui/proactive-forced-colors.png`).
4. **200% / 400% Zoom Reflow (`320 CSS px` width):**
   - At `320x700` CSS px (equivalent to 400% zoom on a 1280 px desktop viewport), `document.documentElement.scrollWidth > window.innerWidth` is **`false`** (`hasOverflow320: false`, `accessibility-audit.json` check #11: `PASS`), and across `1280x900`, `767x1024`, and `390x844` viewports all overflow checks passed (`0` horizontal overflow).
